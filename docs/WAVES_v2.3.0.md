# PROTOCOL ZERO / WAVES 06–10 — релиз v2.3.0

Пять новых волн **реализованы в исходном коде** поверх v1.8.0. Это локальный рабочий продукт и воспроизводимая модель тестирования, а не опубликованная платформа с реальной выручкой. Все внешние рекламные сайты остаются неподключёнными до получения подтверждённых API и доступа.

## WAVE 06 — Клиентские комнаты согласования

**Почему:** бизнесу нужно безопасно показать выбранные рекламные материалы заказчику, не раскрывая черновики, комментарии других людей и приватные сессии.

**Сделано:** `/reviews/BRF-ID` для владельца одобренного брифа; выбор 1–6 **публичных** вариантов одной кампании; замороженные творческие снимки; защищённая случайная URL-ссылка `/review/TOKEN` на 1/7/30 дней; одноразовый показ полного токена; SHA-256 токена в SQLite; ручной отзыв доступа. Гость может просмотреть только явно включённые заголовок, CTA, тон и поколение. При скрытии выбранной ветви модератором комната закрывает публичный доступ.

**Как проверить:** одобрить бриф через CLI; создать публичную ветвь во втором браузере; выбрать исходник и ветвь; сформировать ссылку и открыть её отдельным браузером. Чужой бриф невозможно добавить в комнату. Тесты `waves6-9-commercial.test.js`, `wave10-operator.test.js`.

## WAVE 07 — Голос клиента и журнал решений

**Почему:** сбор отзывов без фиксации последующего решения — ещё один опросник вместо рабочего процесса.

**Сделано:** отзывы 1–5 с пояснением 10–600 символов без регистрации; один отзыв от анонимной сессии на выбранный вариант в данной комнате; доступ к чужим комментариям отсутствует. Автор брифа просматривает отзывы, сохраняет приватную оценку `new / considered / rejected` и до 700 символов заметок. `review_decision_log` не переписывает первоначальное содержание ветви. JSON-экспорт реестра через кабинет. Удаление данных участника удаляет его отзыв.

**Важная граница:** это субъективные оценки приглашённых, не статистика конверсий и не факт оплаты.

## WAVE 08 — A/B Integrity Monitor

**Почему:** подписанные события не должны автоматически становиться «победой рекламного варианта».

**Сделано:** `/api/experiments/EXP-ID/integrity` и кнопка «Проверка данных» в лаборатории. Отчёт считает назначения A/B, подписанные показы, подписанные целевые события, описательные доли и **95%-интервалы Wilson** по показам. Проверка Sample Ratio Mismatch (SRM) при 100+ назначениях: для гипотезы 50/50 используется χ²=(A−B)²/(A+B), флаг при >10,8276 (ориентировочно p<0,001 по χ² с 1 степенью свободы); дополнительное предупреждение о разнице долей экспозиции >15 процентных пунктов, низких выборках, отсутствии live-партнёра. В JSON есть явный отказ от автоматического объявления победителя.

**Граница:** отчёт НЕ проводит независимую сверку событий со сторонними платежами, не гарантирует качество эксперимента, не утверждает причинный uplift. Партнёра нужно проверять отдельно.

## WAVE 09 — Коммерческие пилоты без фальшивой оплаты

**Почему:** спрос нужно подтверждать явным интересом и предложениями, а не регистрациями и пользовательскими поколениями.

**Сделано:** `/pilots/BRF-ID`; запрос с целью и диапазоном бюджета (`unknown`, `<€500`, `€500–2 000`, `>€2 000`); статус `requested`; локальный оператор CLI просматривает запрос, переводит в `reviewing`, отправляет письменное предложение с указанной суммой **в евроцентах**; пользователь в своём анонимном кабинете выбирает принять интерес или отказаться. Статусы имеют строгую state machine, оператор не может сам отметить коммерческое предложение принятым от имени клиента. `pilot_audit` записывает переходы.

**Граница:** `accepted` означает нажатие «подтвердить интерес» на предложении — не заключённый договор, платёж, оказанную услугу, revenue или юридически обязательную электронную подпись. Платежи, инвойсы, CRM и реальный клиент пока не подключены.

## WAVE 10 — Контроль безопасности, миграций и хранения

**Сделано:** отдельные миграции SQLite без удаления старых таблиц/ветвей, owner/session ACL для всех новых endpoints, API-лимиты, приватный токен комнаты (хеш в базе), защита от повторного отзыва, интеграция с существующими `privacy/export` и `privacy/delete`, оператор `doctor` (`PRAGMA integrity_check`, `foreign_key_check`), оператор `commercial-prune` (dry-run и резервная копия перед удалением), новая документация, smoke-тест и тесты. Старые команды запуска и демоплатформа сохранены.

**Ограничения:** анонимная cookie — не корпоративная аутентификация; нет SSO, инвойсинга, криптографической верификации клиента, распределённого rate limit, внешнего pentest, правовой проверки GDPR, публичного production SLA. Никогда не вводите конфиденциальные договоры в открытые ветви.

## Сценарий оператора

```bash
npm run check
npm test
npm run smoke
npm run ops -- doctor
npm run ops -- briefs
npm run ops -- pilots
npm run ops -- pilot-view PIL-ID
npm run ops -- pilot-review PIL-ID "Проверена цель и предварительная смета"
npm run ops -- pilot-offer PIL-ID 85000 "Зафиксирована предварительная стоимость" "Подготовим два рекламных варианта и отчёт о проверке, без гарантий конверсий."
npm run ops -- commercial-prune
npm run backup
npm run ops -- commercial-prune --execute --backup-confirmed
```

Вся операторская зона остаётся **CLI**, не публичным административным API. Перед реальной коммерческой работой требуются отдельные договоры, ответственное лицо, HTTPS, аудит доступа и финансовая инфраструктура.

## Критерии завершённости

1. Старые 44 теста не регрессировали; добавлены тесты пяти новых волн.
2. В независимом браузере открывается гостевая ссылка; оценка записывается в SQLite; владелец видит её отдельно, остальные гости — нет.
3. Отзыв ссылки и модерация блокируют доступ; истечение срока ссылки автоматически проверяется.
4. Нельзя отметить платёж без интегрированного платежного провайдера, нет алгоритма автоматической «победы» A/B.
5. Экспорт и удаление сессии охватывают новые приватные объекты; локальный оператор получает отчёт о целостности базы.
6. Финальный архив повторно распаковывается и проходит автономные тесты без рабочей SQLite и секретов.
