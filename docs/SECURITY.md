# Границы безопасности / антиабьюз

**Выполнено в v1.1.0:**

- Авторство на анонимной подписанной HttpOnly cookie. Для производственного режима обязательны HTTPS и стабильный `SESSION_SECRET`.
- CSRF-защита через проверку Origin и Sec-Fetch-Site, запросы изменений исключительно JSON; заголовки CSP / no-sniff / no-referrer.
- Параметризованные SQL-запросы; неизменяемость публичной генеалогии; транзакции SQLite для критических операций.
- Ограничения количества запросов по IP и сессии в памяти Node, квоты для мутаций/приглашений/жалоб/сохранений.
- Экранирование пользовательских значений при вставке в HTML/SVG; лимиты строк и запрет HTML-тегов в публичной мутации.
- Приватная мастерская проверяет авторство на сервере; другие клиенты не могут прочесть или изменить её через ID.
- Жалобы не раскрываются через пользовательское API; скрытые ветви, их потомки и карточки недоступны публично.
- Провайдерские события принимаются только с валидной HMAC-подписью по сырым байтам тела; `event_id` идемпотентен, конфликтующие повторы отвергаются.
- Удаление сессии включает частные черновики, события, жалобы и отмену текущих приглашений; публичные исторические тексты сохраняются обезличенными.

**Не выполнено и обязательно до массового открытого запуска:**

- Процесс круглосуточной модерации и апелляций, система автоматической проверки вредоносных/оскорбительных высказываний, контролируемые сроки хранения.
- Фильтры угроз и защита от распределённых ботов на reverse proxy/CDN; текущий in-memory rate limiter работает только внутри одного Node-процесса.
- Политика обработки персональных данных конкретного оператора (юридическое лицо, контакт, основания, retention, DPA с поставщиками, процедура запросов субъектов). Этот репозиторий не является юридическим заключением и **не подтверждает GDPR-compliance**.
- Реальная авторизация сотрудников / private B2B workspaces, профессиональное хранение коммерчески конфиденциальных брифов; личные рабочие копии MVP не предназначены для секретной информации.
- Разделение полномочий, централизованный аудит безопасности, penetration test и контроль зависимостей на CI.
- Бэкапы вне сервера и регулярно проверяемое восстановление.

IP-ограничение считает IP прямого TCP-подключения: за reverse proxy несколько посетителей могут делить один адрес. На проде **настройте корректный rate limit на самом reverse proxy** по реальным IP и отдельные ограничения API; не считайте это решённым только встроенной защитой.

`node:sqlite` в Node 22 может выдавать `ExperimentalWarning`. При переходе на другой runtime или SQL backend необходимы повторные интеграционные тесты.

## Новое в v1.2.0: Conversion Bridge

- Партнёры задаются только серверным JSON реестром (не вводом URL от пользователя). В production запрещены HTTP-адреса и демонстрационный режим.
- Секреты только из server environment (минимум 32 символа); разные секреты для разных партнёров.
- `X-PZ-Signature = HMAC-SHA256(secret, timestamp + '.' + raw_body)`; 5-минутное окно и ID событий против повторного создания результата.
- `resolve` требует предварительного перехода автора, `confirm` — предварительного `resolve`; чужие handoff ID не разрешаются.
- Отзыв запрещает новые обращения, но не может удалить уже полученный третьей стороной материал; важный privacy-компромисс.
- `sandbox` всегда отделён от live, не повышает статус ветви до verified.
- Публичные ветви под модерацией нельзя экспортировать по API стороннего партнёра. Автор может отозвать прежнюю передачу и после модерации.
- Ссылка handoff — секретный capability-token: не используйте его в публичных логах и системах аналитики партнёра сверх необходимого.
- Не подключайте неблагонадёжные источники к режиму live; наличие HMAC само по себе не доказывает надёжность провайдера.

Остались за рамками MVP: согласованные SLA партнёров, ротация ключей с перекрытием двух ключей, OAuth/SSO, продвинутый антиспам, контакт для удаления импортированной копии на стороне партнёра, независимый security pentest, distributed rate limiting и полноценная интеграция с Consent Management. Без них публичный массовый запуск рискован.


## v1.3 / Заявки компаний и персональные контакты

- До ручного решения заявка недоступна публичному API, общей ленте, карточкам, партнёрам и поисковым метаданным. Клиент видит только **свои** заявки по серверной проверке browser session.
- Для email требуется отдельный `contactConsent:true`. Email никогда не копируется в таблицы публичных кампаний или в handoff-пакеты. Это контакт **для ответа на заявку**, а не маркетинговая подписка.
- Реальный бизнес требует внешней проверки прав на бренд, рекламных обещаний и допустимости публикации оператором. Галочка в форме **не** является автоматической идентификацией владельца.
- Локальная операторская команда `brief-unpublish` умеет скрыть **весь опубликованный корень** и его потомков. Маршруты `bootstrap`, `branch`, `card`, `lineage`, `invite`, `resolve` отфильтровывают скрытые ветви.
- Личные варианты для заявителя учитывают лишь открытые публичные поколения; нельзя прочитать чужие рабочие копии, контакты, сессии или приватные заметки.
- CSV-выгрузка экранирует потенциальные spreadsheet-formula строки. Это дополнительная защита, не замена проверке файлов.
- SQLite здесь **без шифрования приложения**, анонимный cookie не эквивалентен подтверждённому корпоративному аккаунту. До запуска с настоящими коммерческими данными нужны защита диска и бэкапов, ролевые операторы, политика retention и ответы на GDPR запросы. Не отправляйте секретные клиентские брифы в публичный эксперимент.

## Дополнение v1.8.0

- В новой приватной редакционной таблице `brand_variant_reviews` право доступа подтверждается сессией владельца заявки. Публичный API не показывает заметки.
- A/B планы закрепляются за кампанией и владельцем; снимки объявлений фиксируются в момент планирования. Подписанные webhook-запросы партнёра по HMAC проверяются отдельно от браузерной cookie-сессии.
- `visitorKey` должен быть случайным стабильным псевдонимным токеном партнёра, не email/IP/телефоном. Портал хранит HMAC от токена, но не сам visitorKey; это не заменяет privacy-проверку законных оснований обработки данных.
- Партнёрский backend может ошибаться или злоупотреблять подписанными событиями. HMAC обеспечивает аутентификацию источника запроса, **не** независимую достоверность рекламных продаж.
- Эксперимент отбрасывает неподписанные события, дубли, подмену eventId, goal до impression и показ той же анонимной сущности повторно.
- Операторская команда очистки работает только локально, в режиме dry-run по умолчанию; перед `--execute --backup-confirmed` требуется резервная копия и верификация процедуры восстановления.
- Перед production обязательно: защищённые HTTPS-домены, изолированные секреты/базы, защита от DDoS, аудит целостности, управление доступом операторов и юридическая проверка.

## Дополнение v2.3: клиентские ссылки и коммерческие заявки

- Гостевые review-токены являются bearer capabilities; хранятся только хеши; URL действителен 1/7/30 дней, может быть отозван. Обладатель URL может дать отзыв без регистрации, поэтому **не считать отзыв идентифицированным клиентом**.
- Для гостя открыты только зафиксированные при создании публичные `hook`, `tone`, `cta`; личные workspace, notes, email, другие отзывы и cookie-ID недоступны.
- Owner-only ACL проверяется для списка комнат, приватных отзывов, журнала решений, запросов и предложений пилотов. Операторский доступ только локальный CLI; публичной admin-страницы нет.
- `privacy/export` и `privacy/delete` охватывают `review_rooms`, `review_feedback` и `pilot_requests`; сохранённые публичные ветви остаются без авторства.
- `commercial-prune` и `doctor` выполняются локально, сохраняют разделение live/sandbox и не подтверждают юридическое соответствие.
- Вредоносные тексты комментариев экранируются в UI и проверяются на сервере. Rate limit in-memory; перед массовым выпуском нужны reverse proxy/WAF, аудит cookie-атак, централизованное логирование и внешний pentest.

## Дополнения v2.8.0

Пакеты вариантов и снимки закрытых A/B экспериментов содержат локальный хеш SHA-256, который выявляет изменение данных внутри БД при повторном чтении, но **не защищает от администратора, способного заменить и данные, и хеш**. Эти материалы нельзя выдавать за независимую цифровую сертификацию или подтверждение успешности рекламы. Доступ к ним — исключительно по сессии владельца; скрытые модерацией ветви не выдаются в пакетах.

Пауза кампании блокирует новые изменения и приглашения на стороне сервера; не полагайтесь только на отключение кнопок. Закрытие A/B плана блокирует серверные события партнёра. Локальный операторский CLI имеет повышенные полномочия и должен быть доступен только доверенному администратору. Переносите секреты отдельно от релизного ZIP.
