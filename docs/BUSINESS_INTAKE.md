# PROTOCOL ZERO v1.3 / Брифы реальных рекламодателей

## Что реально реализовано

Публичный `/submit` и меню «Для бизнеса» принимают заявку владельца бренда **без регистрации**. Заявка сохраняется в SQLite со статусом `pending`, не попадает в публичный каталог, брифы партнёров или OG-карточки до **ручной проверки оператором**. Публикация одобренного брифа создаёт отдельную кампанию `BR-*` и исходную ветвь `BR-*-ROOT`; затем другие участники могут наследовать её по общим правилам одного изменения.

Это **не проверка владения брендом**, **не доказательство заявленных свойств**, не объявление о принятом коммерческом заказе и не платёжная функция. На момент выпуска нет подтверждённых реально подключённых рекламных сайтов. Вся информация о новом бренде предоставлена заявителем; оператор обязан проверить право использования и безопасность формулировок вне программы.

## Оператор: работа с очередью

Откройте терминал **на сервере**, где находится база (не выставляйте CLI или SQLite наружу):

```bash
npm run ops -- briefs
npm run ops -- brief-view BRF-ИЗ-ОЧЕРЕДИ
```

`brief-view` покажет **приватные данные заявки, включая email, если он добровольно передан**. Не вставляйте вывод в публичные тикеты и чаты. Выполните ручную проверку: право заявителя представлять бренд; согласованность сайта, бренда и материалов; наличие юридически значимых обещаний и доказательств; отсутствие чужих личных данных и незаконного рекламного контента. Указанный сайт система сама **не открывает**, не скачивает и не проверяет.

Если всё допустимо (кавычки вокруг текста причины обязательны для нескольких слов):

```bash
npm run ops -- brief-approve BRF-ИЗ-ОЧЕРЕДИ "Проверены заявитель, описание и условия публичного теста" --manual-review
```

Если проверка не пройдена:

```bash
npm run ops -- brief-reject BRF-ИЗ-ОЧЕРЕДИ "Недостаточно сведений о праве представлять этот бренд"
```

Состояния `pending → approved`, `pending → rejected`, `pending → withdrawn` — однократные. Повторный review возвращает ошибку. В журнале `brand_review_log` фиксируются решение и причина; решение оператора **не означает независимую юридическую/фактическую экспертизу**.

Если позже выяснится проблема в уже опубликованном бренде, скройте всю его родословную:

```bash
npm run ops -- brief-unpublish BRF-ИЗ-ОЧЕРЕДИ "Жалоба на право публикации требует дополнительной проверки"
```

После проверки можно восстановить публикацию:

```bash
npm run ops -- brief-republish BRF-ИЗ-ОЧЕРЕДИ "Проверены права и получено разрешение на восстановление"
```

Скрытие корня `BR-*-ROOT` запрещает публичный доступ ко всем его потомкам, приглашениям, социальным карточкам и partner handoff. Демонстрационные корни `7F-*` по-прежнему нельзя скрыть через эти команды.

## Что видит заявитель

1. Форму с названиями, аудиторией, задачей, исходным заголовком и призывом, ограничениями по доказательствам и визуалом.
2. Две отдельные обязательные галочки: наличие прав на материал и разрешение на публикацию после ручной проверки.
3. **Необязательный** контактный email только для ответа на заявку; если email указан, требуется третья отдельная галочка. **Email никогда не публикуется в кампании и не используется как маркетинговая подписка.**
4. Приватный список заявок в текущем анонимном браузере, статусы и причину решения. До review может отозвать заявку.
5. После approval — ссылку на опубликованный геном и **«Результаты людей»**: до 500 последних публичных мутаций и выгрузку CSV, с защитой от простых spreadsheet-formula инъекций. Отчёт не содержит личных рабочих копий, email, сессий или редакторских заметок.

Автор брифа **не является автоматически автором всех последующих мутаций**. Он может изучать публичную историю; редактировать чужие частные копии нельзя.

## Маршруты

| Метод | URL | Назначение |
|---|---|---|
| POST | `/api/business-briefs` | Приватная заявка (ответ 201) |
| GET | `/api/business-briefs` | Только заявки текущего браузера |
| POST | `/api/business-briefs/:id/withdraw` | Отзыв ожидающей заявки |
| GET | `/api/business-briefs/:id/variants` | Публичные потомки одобренной кампании **только для её заявителя** |
| GET | `/api/bootstrap` | Каталог демонстрационных и одобренных, не скрытых корней |
| GET | `/api/privacy/export` | Включает собственные заявки и контактные данные |
| POST | `/api/privacy/delete` | Удаляет собственные заявки и контактные данные из локального хранилища |

Все изменяющие пользовательские API принимают JSON и защищены той же подписанной анонимной сессией, Origin/Sec-Fetch-Site, лимитами и серверной валидацией, что и остальная программа. Не внедряйте публичный операторский HTTP-маршрут вместо локального CLI.

### Пример объекта заявки

```json
{
  "brand":"ATELIER NORTH",
  "title":"Короткая история нашей студии",
  "category":"Дизайн",
  "short":"Наша небольшая студия создаёт визуальные решения для локальных компаний.",
  "audience":"Предприниматели, которым нужен фирменный стиль",
  "promise":"Познакомить клиентов с реальными примерами портфолио",
  "evidence":"Работы заявителя находятся в портфолио, другие обещания нужно подтвердить.",
  "visual":"Крупные заголовки и реальные фотографии проектов",
  "hook":"История вашего бренда заслуживает внимания",
  "tone":"Деловой",
  "cta":"Посмотреть наше портфолио",
  "website":"https://example.org/",
  "contactEmail":"",
  "contactConsent":false,
  "rightsConfirmed":true,
  "publicConfirmed":true
}
```

Отсутствие прав на материал, нарушение ограничений по длине и опасные протоколы внешних URL — ошибки валидации. Это не исключает неподтверждённые фактические заявления, поэтому проверка оператором обязательна.

## Реальные ограничения

- Нет автоматической проверки владения сайтом и юридического статуса заявителя, независимого фактчекинга, SLA рассмотрения или системы переписки с рекламодателем. Оператор сможет **самостоятельно** ответить на добровольно указанный email.
- Анонимное авторство закреплено за browser cookie. После очистки cookie пользователю не гарантируется возможность восстановить своё авторство.
- Пользователь может удалить собственную заявку через privacy delete. Публичный геном одобренной кампании и созданные другими людьми потомки сохраняются в рамках опубликованной истории; оператор может скрыть их через `brief-unpublish`. Это важно объяснить до согласия на публикацию.
- Контактный email хранится в SQLite **без шифрования на уровне приложения**. До открытого запуска требуется защитить диски и бэкапы, задать сроки хранения и формальные документы оператора; если эти условия не обеспечены, не принимайте персональные данные публично.
- CSV отражает реальные тексты и статусы, **не** результаты A/B-тестов, окупаемость рекламы, продажи или endorsement бренда.
