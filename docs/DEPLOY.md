# Развёртывание и обновление

## Обновление v1.0.0 → v1.1.0

1. Остановите прежний сервер через Ctrl+C или `docker compose down`.
2. **Сделайте резервную копию** исходной `data/protocol-zero.sqlite`, а также отдельно сохраните `data/.session-secret` или production `SESSION_SECRET`.
3. Распакуйте новые исходники в новую папку. В локальном варианте перенесите содержимое `data/` из предыдущей версии, если вам нужна именно старая база.
4. Запустите `npm test` **до** запуска реальных данных. Затем `npm start`.
5. `openDatabase()` автоматически добавит новое поле moderation status и таблицы рабочих копий/жалоб. Корни и реальная родословная не удаляются.
6. Проверьте старые ветви, старые приглашения, затем новый частный черновик и `npm run ops -- queue`.
7. Выполните `npm run backup` после миграции и сохраните результат отдельно.

**Не включайте `data/` с реальными сеансами и секретами в Git и пользовательские ZIP.** Релизный архив содержит только `data/.gitkeep`.

## Локальная работа

```bash
node --version    # >= 22.13
npm start
# http://127.0.0.1:8787
```

## Docker + HTTPS

```bash
cp .env.example .env
# задайте сильный SESSION_SECRET, PUBLIC_URL=https://ВАШ_ДОМЕН
# остальные переменные настройте только по подтверждённым данным

docker compose up -d --build
curl http://127.0.0.1:8787/api/health
```

Compose ограничивает опубликованный порт `127.0.0.1:8787`. Перед ним нужен управляемый reverse proxy, который выдаёт публичный HTTPS-сертификат и гарантирует защиту от нестандартных `Host`/`Forwarded` заголовков. Пример Caddy:

```
your-real-domain.example {
    encode zstd gzip
    reverse_proxy 127.0.0.1:8787
}
```

В Docker одна копия Node + один SQLite writer. Размножать контейнер на несколько серверов **нельзя** без перехода к общей SQL-базе. Дополнительные условия: защита от DDoS, логирование без секретов и персональных текстов, аудит бэкапов, подтверждённая юридическая политика и контакт для жалоб.

## Аналитика

`npm run ops -- report` показывает локальные реальные события. Не сравнивайте экспериментальные 20–50 тестовых участников с массовой конверсией. Показатели в отчёте не являются отраслевыми нормативами. Отдельно различайте `client`, `self_report`, `webhook`.

## Внешняя интеграция

```bash
# Linux/macOS example:
PLATFORM_NAME='Платформа 1' PLATFORM_URL='https://real-product.example' npm start
```

Система передаёт результат пока только через **копирование готового брифа** и открытие настроенной ссылки. Не дописывайте данные кампании в URL с секретами: query-string может попадать в историю браузера и логи. Гарантированное подтверждение требует доверенного server-to-server webhook; см. `API.md`.

## Обновление 1.1.0 → 1.2.0

Остановите старый экземпляр, проверьте и сохраните `data/protocol-zero.sqlite` и `.session-secret` отдельно. Приведённые в архиве `data/` и `config/` не содержат реальных сессий или паролей. Скопируйте старую `data/` в новую папку; выполните `npm run check && npm test`; после этого `npm start`. Новая версия добавляет таблицы `handoffs`, `partner_receipts`, индексы, без удаления существующих ветвей, приглашений и рабочей мастерской.

Новый параметр `PZ_PLATFORMS_FILE` задаёт путь к JSON-реестру. Без него список платформ пуст, но остальное приложение запускается как прежде. Для Docker образ копирует каталог `config/` (примерные файлы без ключей). Для реального продукта **монтируйте** отдельный private `platforms.live.json` и передавайте секреты через защищённые переменные окружения. Никогда не используйте демонстрационный adapter в `NODE_ENV=production`: сервер запретит запуск.

**Развёртывание не выполнено:** это инструкции, не факт публикации. `npm run demo` используется только локально, не выставляйте демо-порт 8790 в интернет.


## Миграция v1.2.0 → v1.3.0 и реальные заявки

1. Остановите старые серверы. Сохраните `data/protocol-zero.sqlite`, WAL/SHM только в корректной остановленной базе или через поддерживаемый `npm run backup`; обязательно сохраните `data/.session-secret`/`SESSION_SECRET`.
2. Распакуйте новую сборку в отдельный каталог и перенесите `data` с необходимыми данными. **Не заменяйте файлы запущенной программы.**
3. Запустите `npm test`, затем `npm start`. При первом открытии SQLite произойдёт неразрушающая миграция: новые таблицы заявок и их решений, поле `campaigns.origin`.
4. Проверьте старый приглашённый переход, личные рабочие копии и реальные сохранённые handoffs, затем новый путь `/submit`.
5. `npm run ops -- briefs` должен работать после запуска мигрированной версии.
6. Сохраните резервную копию после успешного запуска. Старый бинарник приложения **не предназначен** для работы с данными новых заявок.

Если включаете приём реальных брендов, обеспечьте защиту хранения добровольно переданного email, юридические документы оператора, процедуру подтверждения полномочий заявителя и снятия публикаций. Эти меры **не реализованы автоматически**.

## v1.8.0 — обновление, мониторинг, очистка

Перед обновлением с v1.3: остановить процессы, сохранить `data/`, сессионый секрет и конфигурацию платформ; на копии базы проверить запуск v1.8 и новые таблицы A/B, а также `last_seen_at`. `npm run ops -- prune` безопасно показывает кандидатов без удаления. Применяйте `npm run ops -- prune --execute --backup-confirmed` только после резервной копии и проверки восстановления.

Проверки новой сборки: `npm run check`, `npm test`, `npm run smoke`, `npm run verify:release`. Health: `GET /api/ready` (200 при доступной SQLite). Закрытые операторские команды `npm run ops -- experiments` и `npm run ops -- report` не публикуют web-admin.

База данных хранит анонимные сессии и заявленные данные компании; их режим обработки перед production должен быть согласован юридически. Документы: `docs/AB_EXPERIMENTS.md`, `docs/DATA_RETENTION.md`, `docs/WAVES_v1.8.0.md`.

## Обновление v1.8.0 → v2.3.0

1. Остановите предыдущий сервер. Сохраните SQLite **с WAL/SHM** корректным инструментом SQLite (`npm run backup`), а также `.session-secret`/`SESSION_SECRET` и приватные настройки платформ.
2. Проверьте восстановление копии в отдельной директории, затем запустите v2.3.0 на этой копии. Новые таблицы `review_rooms`, `review_feedback`, `review_decision_log`, `pilot_requests`, `pilot_audit` создаются аддитивно; публичные ветви, токены приглашений и существующие эксперименты сохраняются.
3. Выполните `npm run check && npm test && npm run smoke && npm run ops -- doctor`. Подтвердите `integrity:["ok"]`, `foreignKeyErrors:0`. Перед удалением каких-либо записей сначала `npm run ops -- commercial-prune` (dry-run).
4. Включите обратный HTTPS proxy, проверку корректной смены сессий, изоляцию операторского CLI и журналов. Не используйте логи запросов с секретными review-токенами, если можно избежать.
5. Не называйте коммерческий `accepted` оплаченной покупкой: платёжного сервиса нет. Live A/B данные остаются недоступными, пока не настроен реальный HMAC партнёр.

Приложение не выполняет внешнюю юридическую проверку прав на бренд, достоверности рекламных заявлений и личностей клиентов. Перед публичным запуском из ЕС нужны контакты контроллера данных, документы, процедуры отзыва/удаления и реальная оценка безопасности.

## Обновление на v2.8.0 — WAVE 11–15

Перед обновлением **остановите** сервер v2.3.0, сделайте резервную копию SQLite штатной командой `npm run backup`, сохраните `data/.session-secret`, переменные окружения и закрытый JSON реестр платформ. Тестируйте миграцию на копии. Не переносите старые `src/`/`public/` поверх новой версии: сначала распакуйте новый ZIP в чистый каталог, затем перенесите только данные и секреты.

Новая миграция аддитивно добавляет `campaign_controls`, `campaign_control_log`, `creative_packs`, `experiment_closures`, `pilot_milestones`, `pilot_milestone_log`. Кнопки WAVE 11–15 доступны в «Центре бизнеса» одобренного брифа. Повторный запуск миграции должен быть безопасен. Контрольная проверка: `npm run check && npm test && npm run smoke && npm run verify:release`; для проверки БД используйте `npm run ops -- doctor`.
